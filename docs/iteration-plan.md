## 已完成回顾（v1.0）

小程序已跑通完整的 MVP 闭环：

- **账号体系**：微信手机号登录 + 测试用户登录 + 本地 Mock 模式
- **用户画像**：性别/年龄/身高/体重/目标 → 自动生成热量及营养素方案
- **食物记录**：四层解析架构（规则引擎 → 烹饪方法剥离 → 复合菜品库匹配 → DeepSeek AI 兜底），双食材库 890 条
- **运动记录**：有氧/轻度力量/中度力量/重度力量，根据体重和时长计算消耗
- **首页看板**：今日进度条、营养素进度、餐饮分组列表、记录表展开/折叠
- **趋势页**：周/月维度 Canvas 折线图，BMR 和目标摄入基准线
- **个人页**：紧凑资料卡，热量方案公式展开
- **测试覆盖**：plan / foodParser / exercise / summary / aiResolver / stats / authSession / cloudBootstrap / pageCache 共 9 套 Jest 测试

## Phase 1：体重追踪（当前进行中）

目标：完整的体重记录、趋势可视化和智能方案调整。

### 1.1 数据层

- [ ] **新增 `weight_records` 数据库集合**：字段 `userId`、`date`、`weight`（kg，精确到 0.1）、`note`、`createdAt`、`updatedAt`
- [ ] **新增云函数 `addWeightRecord`**：写入体重记录，同一日期覆盖更新（每天一条）
- [ ] **新增云函数 `getWeightRecords`**：按 userId + 时间范围查询，返回列表和统计（初始体重、当前体重、变化量、BMI 趋势）
- [ ] **`saveProfile` 联动**：修改资料中的体重时，自动生成一条当天体重记录
- [ ] **体重变化量计算**：基于初始体重（取最早记录或 profile 初始体重）计算累计变化

### 1.2 前端页面

- [ ] **首页增加体重卡片**：在营养卡片下方展示当前体重、变化趋势箭头、目标进度条
- [ ] **体重记录弹窗**：从首页体重卡片点击进入，输入今日体重（默认回填上次记录），支持可选备注
- [ ] **趋势页增加体重 Tab**：在现有"本周/本月"切换基础上，增加"体重"维度，展示体重变化折线图和目标线
- [ ] **体重趋势 Canvas 组件**：复用 `trend-chart` 组件逻辑，新增 `weight-chart` 组件展示体重变化
- [ ] **历史记录列表**：支持查看过往体重记录，可编辑或删除

### 1.3 智能化

- [ ] **热量方案动态调整提示**：当体重变化超过 2kg 时，首页和资料页提示用户重新计算热量方案
- [ ] **目标体重进度**：资料编辑页增加"目标体重"字段，首页展示从初始体重到目标体重的可视化进度
- [ ] **BMI 自动计算**：基于当前身高和体重，展示 BMI 数值和健康区间

## Phase 2：核心体验打磨

目标：修掉已知体验问题，提升日常使用的流畅感。

### 2.1 已确认的体验问题（从代码检查发现）

- [ ] **删除二次确认**：首页食物和运动记录点删除直接生效，需增加确认弹窗（`wx.showModal`）
- [ ] **API Key 安全**：`parseFoodInput/index.js` 第 10 行硬编码 DeepSeek Key，迁移到环境变量（`decomposeDish` 已支持 env var，统一方案）
- [ ] **首页首次闪白**：`loading: true` 导致无缓存时内容区不渲染，可改为用缓存数据立即渲染 + 异步刷新
- [ ] **内容安全**：用户输入未接入 `msgSecCheck`，虽然是低风险但建议补上

### 2.2 交互优化

- [ ] **运动时长快捷选项**：15min / 30min / 45min / 60min 一键填入
- [ ] **食物历史快捷填入**：记录食物时支持从近期记录快速选择
- [ ] **食物解析结果可编辑**：解析后的克重、热量允许用户手动修正
- [ ] **首页记录排序**：确认餐饮分组按餐次固定顺序（早→午→晚→加餐）
- [ ] **运动消耗公式透明化**：在运动记录弹窗中预览估算消耗

### 2.3 稳定性

- [ ] **云函数全局超时处理**：DeepSeek 调用设置 3s 超时，网络异常给出友好提示
- [ ] **云函数冷启动监控**：统计各云函数冷启动耗时，特别是 `parseFoodInput` 加载 890 条数据
- [ ] **食物库数据校验脚本**：确认 `foods.json` 和 `composite_dishes.json` 无重复 ID、无缺失字段

## Phase 3：AI 解析增强

目标：提升食物识别准确率和响应速度，减少"未识别"。

### 3.1 解析准确率

- [ ] **命中率埋点**：在 `parseFoodInput` 中统计四层各自命中率，数据存 `dish_cache` 或 console 日志
- [ ] **常见失败案例补充**：从使用数据中收集未识别食物，定期补充到 `composite_dishes.json`
- [ ] **烹饪方法库扩展**：当前 11 种方法，补充"清炒/爆炒/干煸/蒜蓉/麻辣"等
- [ ] **餐厅菜品库**：补充外卖常见菜品（黄焖鸡、麻辣烫、酸菜鱼等），至少 50 个
- [ ] **中文量词同步**：Mock 版已支持"一碗米饭"等，确认云函数解析层同步
- [ ] **AI Prompt 迭代**：根据失败案例优化 DeepSeek 分解 prompt

### 3.2 响应速度

- [ ] **AI 请求超时 + 降级**：DeepSeek 调用 3s 超时，回退到"整体食材"兜底
- [ ] **AI 结果缓存**：成功分解的菜品写入云数据库 `dish_cache`，下次直接命中
- [ ] **批量 AI 合并**：用户输入 3+ 个未识别食物时，一次 AI 调用处理多个

## 技术债

| 项目 | 严重程度 | 说明 |
|---|---|---|
| API Key 硬编码 | 中 | `parseFoodInput/index.js:10` 硬编码 DeepSeek Key，需迁移到环境变量 |
| 删除无确认 | 中 | 首页记录删除直接生效，易误操作 |
| 首页闪白 | 低 | 无缓存时首屏空白，体验不佳 |
| shared 模块重复 | 低 | 每个云函数各自复制 shared 目录，应用 Layer 统一管理 |
| fallbackParse 重复 | 低 | `food-add` 和 `home` 页各有一份相同的解析逻辑 |
| foods.json 内存 | 低 | 890 条数据通过 require 加载，后续增长需切换为数据库查询 |
